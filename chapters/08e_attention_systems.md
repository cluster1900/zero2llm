# 系统进阶（P15）：FlashAttention、PagedAttention 与服务调度 {#p15-attention-systems}

[上一章](#p14-grouped-kv)的 S4 已经有 RoPE、RMSNorm、SwiGLU 和 GQA。这一章**不再修改模型架构**，而是把镜头移到执行模型的系统：同一条注意力公式，怎样计算、怎样存储、怎样同时服务不同请求？

配套 [code/16_attention_systems.py](../code/16_attention_systems.py) 是独立的 CPU 教学实验。必修部分只用 Python 标准库，不下载模型，不安装 vLLM，也不需要 PyTorch。它包含分块在线 Softmax、分页 KV 所有权模拟、请求时间线算术；**不是 CUDA 实现，不是 FlashAttention 或 vLLM 性能复现**。S4 主线仍保留在原文件中。

## P15.1 一间餐厅里的三个不同问题

想象餐厅同时接到很多订单：

- 厨师怎样在操作台上处理食材，减少来回搬运？这是**计算 kernel** 层。
- 每份订单的食材放在哪些储物格里，哪些可以共享，什么时候释放？这是**KV 内存管理**层。
- 哪个订单先做，做完一部分后能否让新订单加入？这是**请求调度**层。

这三个问题会相互影响，但不能混成一种“新注意力架构”：

| 层次 | 代表机制 | 主要回答 | 不等于什么 |
| --- | --- | --- | --- |
| 计算与 IO | FlashAttention | 怎样分块计算并减少显存读写 | 不是只看部分 token 的稀疏注意力 |
| KV 存储与访问 | PagedAttention + 块管理器 | 怎样通过块表读取不连续 KV，分配和共享缓存 | 不只是把一个大数组切几段，也不是换成 GQA |
| 请求调度 | continuous batching | 哪些请求参加下一轮计算 | 不会消除同一请求的自回归依赖 |
| 跨请求复用 | prefix caching | 哪段已算出的共同前缀 KV 可以复用 | 不是查到相似句子就能复用答案 |

PagedAttention 有配合分页布局读取 KV 的注意力计算方式；块管理器负责分配、引用计数等生命周期。为了看清职责，本章把它们放在内存这一层讲，但不能把真实 PagedAttention 简化成“只有一个 Python 字典”。[PagedAttention 原论文 v1，§4](https://arxiv.org/html/2309.06180v1#S4)

![注意力服务的计算、KV 存储与请求调度三个层次；共享尾块在写入时复制](assets/diagrams/p15-attention-systems.svg)

类比的边界：GPU 不是逐单做菜的厨师，KV 不是文本食材。并行度、带宽、数据类型、模型和调度策略都会影响结果；下面的餐厅比喻不能推出某种方法一定更快。

## P15.2 算术不变，搬运量可以改变

普通注意力的熟悉写法是：

```text
S = Q Kᵀ / √d
P = softmax(S + mask)
O = P V
```

如果 Q、K 都有 N 个位置，S 和 P 各有 N×N 个数。以单个 batch、单个头、每数 2 字节举例：

- N=4096：一张矩阵有 16,777,216 个数，占 33,554,432 字节，也就是 32 MiB。
- N=8192：一张矩阵占 128 MiB；长度翻倍，面积变成 4 倍。
- 如果实现同时保存 S 和 P，这两张矩阵的容量还要相加；实际峰值取决于实现，不能只靠这个公式断言。

这里 MiB=2²⁰ 字节，不是十进制 MB。多 batch、多头会继续乘上相应维度。

GPU 有容量较大的设备显存（原论文讨论的 GPU 使用 HBM，其他 GPU 也可能使用 GDDR）和容量较小、访问更近的片上存储。把完整 S 写回显存、再读回来做 Softmax、再写 P，会产生额外 IO。**FlashAttention 的核心是按片上存储条件分块组织计算，用在线 Softmax 累积输出，避免把完整 N×N 中间矩阵写到 HBM。** 它没有因此跳过普通稠密注意力的所有合法 QK 配对；标准稠密情形的算术复杂度仍为 O(N²d)，不是 O(Nd)。[FlashAttention 原论文（arXiv 2205.14135v2），§3](https://arxiv.org/pdf/2205.14135v2)

这还涉及 GPU 内核融合、线程组织、反向传播重计算等。本章只实现其中容易手算的**前向归一化递推**。Python 列表复制、解释器开销、输入 mask 都与真实 GPU kernel 不同，不能用本脚本的运行时间或进程内存证明 FlashAttention 的收益。

## P15.3 先把形状缩到一个头

暂时去掉 batch 和多头轴，只看一个头，允许 Q/K 长度不同，也允许 V 的宽度不同：

| 名称 | 形状 | 含义 |
| --- | --- | --- |
| Q | [Nq,d] | 当前要计算的 query |
| K | [Nk,d] | 可读取的全部 key |
| V | [Nk,dv] | 对应 value |
| allowed | [Nq,Nk] | 布尔 mask；True 表示允许读取 |
| O | [Nq,dv] | 每个 query 的加权输出 |

本例默认 query block 为 2 行，key block 为 3 行。Nq=5、Nk=7 时，query 分成 `[2,2,1]`，key 分成 `[3,3,1]`。最后一块不满也必须处理，不能直接用整数除法把它丢掉。

为方便观察，脚本可接收完整布尔 mask；这张教学 mask 本身仍可能占 O(Nq×Nk) 空间。生产 kernel 可以由位置索引直接形成因果约束。本实验没有宣称整个 Python 程序只占线性内存。

对于已有 3 个历史位置、当前有 2 个新 query、总共 5 个 key 的例子：

```text
query 的绝对位置：3、4
key 的绝对位置：  0、1、2、3、4
allowed 第 0 行：  1、1、1、1、0
allowed 第 1 行：  1、1、1、1、1
```

`causal_mask(2, 5, offset=3)` 正是这个矩形 mask。不要把新 query 的局部编号 0、1 当成绝对位置，否则第一行会误删历史上下文。

## P15.4 在线 Softmax：只记三本账

只看某一行 query。对已经处理过的合法分数 s_j，记录：

```text
m   = 已处理分数的最大值
ell = Σ exp(s_j - m)
acc = Σ exp(s_j - m) × v_j
```

m 和 ell 是标量；acc 是 dv 维向量。最后输出 `acc / ell`。注意 acc 还没有归一化，不是当前已经算好的概率均值。

现在读到下一块，合法分数为 s_new。新的最大值可能变大：

```text
next_m = max(m, max(s_new))
alpha  = exp(m - next_m)
p_new  = exp(s_new - next_m)

next_ell = alpha × ell + Σ p_new
next_acc = alpha × acc + Σ p_new × v_new
```

为什么必须乘 alpha？旧账用的是 exp(s−m)，新账用的是 exp(s−next_m)。利用指数运算：

```text
exp(s - next_m) = exp(s - m) × exp(m - next_m)
```

所以旧分母和旧分子必须一起换到新尺度。只缩放其中一个，或者把每块 Softmax 后的输出直接相加，都不对。

初始状态设 `m=-∞, ell=0, acc=0`。第一次读到合法分数时，代码直接令 alpha=0，不去做不必要的无穷运算。

## P15.5 手算：分成两块，仍然得到 6

设 d=dv=1，Q=`[1]`，K=`[0, ln 2, ln 4]`，V=`[2,4,8]`。缩放分母 √d=1，三个分数正好就是 K。没有 mask。

先做完整计算：三个指数之比为 1:2:4，因此：

```text
权重 = [1/7, 2/7, 4/7]
输出 = (1×2 + 2×4 + 4×8) / 7 = 42/7 = 6
```

现在把 key 分成前两个和最后一个，块长 `[2,1]`。

第一块：

```text
m = ln 2
p = [1/2, 1]
ell = 1/2 + 1 = 1.5
acc = (1/2)×2 + 1×4 = 5
```

第二块的分数 ln 4 更大：

```text
next_m = ln 4
alpha = exp(ln 2 - ln 4) = 1/2
p_new = [1]
next_ell = (1/2)×1.5 + 1 = 1.75
next_acc = (1/2)×5 + 1×8 = 10.5
输出 = 10.5/1.75 = 6
```

如果错把两个块各自的均值再平均，会得到 `(5/1.5 + 8)/2 = 17/3`，约 5.6667，不是 6。块的概率质量不同，不能给每块相同权重。

## P15.6 逐行看实现，不要只记公式

`blocked_attention()` 的核心如下；完整输入校验和循环在配套脚本中：

```python
next_m = max(m, max(scores))
alpha = 0.0 if ell == 0.0 else math.exp(m - next_m)
weights = [math.exp(s - next_m) for s in scores]
ell = alpha * ell + math.fsum(weights)
acc = [alpha * acc[c] + math.fsum(w * v[j][c] for w, j in zip(weights, visible))
       for c in range(len(acc))]
m = next_m
```

1. scores 只包含当前块中允许读取的 key。
2. next_m 取旧块、新块的共同最大值，不是只记新块的最大值。
3. alpha 把旧的 ell、acc 转换到同一个尺度。
4. weights 仍是未归一化的指数权重，不是单块概率。
5. 每个 value 通道 c 有自己的分子，但共享分母 ell。
6. 所有 key 块结束后才做 `acc/ell`。

脚本按 query 块组织外循环，再逐行遍历 key 块。它故意使用可读的标量循环，没有 GPU 的矩阵 tile、片上共享存储布局或 warp 调度；“有两个块长参数”不等于写出了 FlashAttention kernel。

### 全 mask 是一个单独的边界

若某个块没有合法 key，直接跳过，不计算 `max([])`。若整行都没有合法 key，本教学 API 明确返回全零向量。

这是 API 的安全约定，**不是说空集合上的 Softmax 有正常的概率分布**。直接把全行填成 −∞ 再算 `exp(s-max(s))`，可能遇到 `−∞−(−∞)` 而产生 NaN。测试特意覆盖：

- 第一块全被遮住，后面才出现合法 key。
- 后面的合法分数比前面大，需要重新缩放。
- 整行全被遮住，最终返回零。

分数 10000、10001、10002 也不需要直接算 exp(10002)。减去最大值后，最大指数是 exp(0)=1。输入 Q/K/V 要求有限，点积本身若已经溢出也会拒绝；稳定 Softmax 不能挽救此前已经算成无穷的点积。

## P15.7 “精确注意力”不是“逐 bit 相同”

这里的精确，是指没有用稀疏采样、低秩近似等方法改变这条注意力公式所包含的合法配对。换一种加法顺序、分块顺序或累积精度，浮点末位仍可能不同。

必修实验用 Python float，通常对应双精度浮点；随机例子固定 seed=15。5 个 query、7 个 key、d=3、dv=2 时，本次 full/block 最大差值为 `1.11e-16`，检查阈值为 `1e-12`。这是这组小输入的数值检查，不是任意长度、任意 dtype 都具有相同误差的证明。

只有 full/block 相等还不够：两条路径可能一起忘记 √d。测试另外使用标准库 Decimal 的 **65 位精度独立参考**，逐 query 直接算点积、指数和归一化，不调用生产实现的输入辅助函数、Softmax 或 block 更新。手算的 6 又提供了更容易人工核验的锚点。

这与 GQA 的区别也很重要：GQA 改变 KV 头的组织方式；在线 Softmax 只是计算同一组 Q/K/V 的方式。不能用这章的数值等价实验证明任意 MHA 改 GQA 都不损失质量。

## P15.8 KV 为什么要分页

生成过程中，每个请求的 KV 逐渐增长，但通常事先不知道最终会生成多长。

如果按最大长度为每个请求预留一整片空间，可能空着很多暂时甚至永远用不到的位置；要求请求拥有一整段连续空间，也会限制分配与共享的灵活性。

分页的基本做法是：把 KV 划为固定 token 数的物理块，请求只保留“逻辑第几块放在哪个物理块”的块表。逻辑 token 顺序不变，物理位置不必连续。它降低的是存储管理中的浪费，**不是删除某些历史 token 的信息路径**。

设块大小为 b，某 token 的逻辑位置为 t：

```text
逻辑块号 = t // b
块内偏移 = t % b
物理块号 = block_table[逻辑块号]
```

例如 b=2，块表是 `[1,2,0]`。逻辑位置 4 在逻辑块 2、偏移 0，对应物理块 0。读取时必须按 `[1,2,0]`，不能为了“排序整齐”改成 `[0,1,2]`。

生产 PagedAttention 根据这种映射读取 KV 并计算注意力。本脚本的 `read()` 则为了方便检查，先重建普通 Python K/V 列表，再调用普通 CPU 注意力。这个复制路径**不具有生产分页 kernel 的内存优势**。

## P15.9 先有共享，再谈写时复制

`PagedKVCache` 保存四类状态：

| 状态 | 含义 |
| --- | --- |
| `_blocks` | 物理块号 → 这个块已写入的 KV 载荷 |
| `_tables` | 请求名 → 有序的物理块号列表 |
| `_lengths` | 每个请求当前的逻辑 token 数 |
| `_refs` | 每个物理块被多少个活跃请求引用 |

它模拟单层、单 KV 头；每个 token 的 K 和 V 都是真实的数值向量，但这里不是模型训练得到的表示。为了手算，设 b=2，用 10、20、30 这些数字代表载荷。

A 有三个 token：

```text
A 的块表：[0,1]
物理块 0：[10,20]，引用计数 1
物理块 1：[30,空]，引用计数 1
```

现在 `fork("A", "B")`，让 B 从完全相同的历史继续生成：

```text
A 的块表：[0,1]
B 的块表：[0,1]
物理块 0、1 的引用计数都变为 2
```

此时只是增加块表引用，没有复制 payload。B 接下来要写入 40，尾块 1 却仍被 A 使用。直接写入可能污染另一条分支，所以执行 **copy-on-write，写时复制**：

1. 先分配新的物理块 2，把旧尾块中的 30 复制进去。
2. 旧物理块 1 的引用计数从 2 减到 1。
3. B 的块表改为 `[0,2]`，物理块 2 的引用计数为 1。
4. 把 40 写到物理块 2，得到 `[30,40]`。

A 仍然是 `[10,20,30]`，B 是 `[10,20,30,40]`；完整前缀块 0 继续共享。这一机制与原论文的分叉采样场景一致。[PagedAttention v1，§4.4](https://arxiv.org/html/2309.06180v1#S4.SS4)

### 满块边界不要复制错

如果 A 原本正好只有 `[10,20]`，共享的是一个已满块。B 追加 30 时，直接分配**下一个逻辑块**即可，不必复制已满的前缀块。COW 针对的是要写入的共享未满尾块，不是每次生成都复制全部历史。

若尾块的引用计数已经是 1，也能直接写入，不必复制。请求释放时只减少它所引用块的计数；降到 0 的物理块才回到空闲池。脚本的空闲块可以再次分配，但旧数据必须清掉。

## P15.10 用槽位记账，不伪造显存数字

上面的分叉实例可以独立数出来：

| 时点 | 所有请求逻辑 token 合计 | 实际物理载荷数 | 已分配槽位 | 空槽位 |
| --- | --- | --- | --- | --- |
| A 有三个 token | 3 | 3 | 4 | 1 |
| B 刚 fork，还未追加 | 6 | 3 | 4 | 1 |
| B COW 后追加 40 | 7 | 5 | 6 | 1 |

最后一行不是物理存了 7 个 token，因为 `[10,20]` 仍共享；也不是只存 4 个，因为尾部的 30 已各有一份。

若每个物理载荷只有一个 K 标量和一个 V 标量，且真正使用 float32 数组，则“5 个已写载荷”的理想 payload 是 `5×2×4=40` 字节，“6 个已分配槽位”的理想容量是 48 字节。**本脚本使用 Python 对象，不实际只占这些字节。** 块表、引用计数、对象开销、分配器、临时工作区和模型权重都不在这个理想账本里。

对没有共享的一个长度为 T 的请求，分配槽位是 `ceil(T/b)×b`，尾块空槽位范围为 0 到 b−1。例如 b=4、T=9，需要 3 块，共 12 槽位，空 3 个。分页不是“所有浪费严格等于零”；块越大、越小也有不同管理和访问开销。

池容量不足时，`append()` 会在改变块表和引用计数前报告 `MemoryError`。测试检查失败后 A/B 数据和所有权完全不变。这里没有实现 GPU 抢占、交换到 CPU 或重计算恢复；不能把异常提示当成完整服务系统的容错方案。

## P15.11 Prefix caching：复用的是同一段计算历史

假设两个请求都以完全相同的系统提示开头，后面的提问不同。已经算好的共同前缀 KV 有机会直接复用，减少第二个请求的重复 prefill 工作；它不是为每一个后续 decode token 免掉注意力计算。[vLLM 0.6.4 APC 文档快照](https://docs.vllm.ai/en/v0.6.4/automatic_prefix_caching/apc.html)

但“出现同一个 token”远远不够。KV 依赖它之前的上下文，还依赖模型权重、位置处理和适配器等计算设置。可复用的应是**兼容计算环境下相同的 token 前缀**，不是语义相似句子，也不是任意两段文字中碰巧相同的后缀。

本脚本故意分开两个 API：

- `fork(source, target)`：已经知道整段历史完全相同，可以共享未满尾块，未来写入时 COW。
- `share_prefix(source, target, tokens)`：由调用者先确认前缀兼容，只接收完整块边界。例如 b=2，来源长度 5，可以共享前 4 个 token；要求共享前 3 个会报错。

完整块边界是这个教学 API 的简化契约，不是所有缓存系统只能这样设计。真实 APC 还需要前缀标识、查找、失效规则、淘汰策略以及正确的请求隔离；固定版本 vLLM 文档说明了块级缓存查找的设计。[vLLM 0.6.4 实现说明](https://docs.vllm.ai/en/v0.6.4/automatic_prefix_caching/details.html)

脚本没有实现这些查找和安全机制，也不会检查两个文本是否相同。它还没有“请求结束后仍保留的前缀缓存”引用：所有活跃请求释放后，物理块就释放了。因此不能把这个块表模拟当成可部署的 APC 服务。

这里引用 0.6.4 是为了固定机制说明的文档快照，**不是说它是当前最新版或建议安装的版本**。本章不需要安装任何版本的 vLLM。

## P15.12 Continuous batching：不要让空位等整桌结束

普通静态 batch 可能要等同一批里最长的请求完成，才接下一批。Continuous batching 在每轮计算边界移除已结束请求，再把符合资源条件的新请求加进来。

做一个完全明确的玩具：

- 有两个 decode 槽位，每轮固定 10 ms。
- A、B 在 t=0 已经可以 decode，分别还需要 2、4 个输出 token。
- C 在 t=10 可以 decode，还需要 2 个输出 token。
- **所有 prompt 已在别处完成 prefill；这里只模拟 decode 槽位。**
- 每个活跃请求每轮产出一个 token，时间戳记在本轮结束时。

| 时间段（ms） | 静态 batch | 连续 batch |
| --- | --- | --- |
| 0–10 | A、B | A、B |
| 10–20 | A、B；A 随后完成 | A、B；A 随后完成 |
| 20–30 | 空位、B | C、B |
| 30–40 | 空位、B；B 随后完成 | C、B；两者随后完成 |
| 40–50 | C、空位 | 已结束 |
| 50–60 | C、空位 | 已结束 |

C 在 t=10 到达时，两槽仍被占用，所以连续 batch 也不是立刻开始。它到 t=20 才进入，两个输出时间为 30、40 ms；静态 batch 则是 50、60 ms。

两种方法都完成 8 个输出 token。按这个人造观察窗口，静态是 `8/0.06≈133.333` tokens/s，连续是 `8/0.04=200` tokens/s。**这些是固定轮时假设推出来的数字，不是 GPU 实测，也不是“连续 batch 一定快 1.5 倍”的结论。**

真实 batch 大小会影响轮时，KV 不够也可能不能接入新请求。更多并发可以提高总吞吐，但单请求等待或 token 间隔可能变长。必须把每轮执行时间和排队一起看。

## P15.13 Prefill、decode 与排队会互相影响

Prefill 一次处理已知 prompt 的很多位置，decode 沿着输出依赖一步一步走。把一个很长的新 prompt 放进服务计算，可能延后其他请求的下一次 decode。

调度器可以选择分块 prefill、限制每轮 token 预算、为不同请求设置优先级等。这些策略会在首 token 等待、后续 token 间隔和总吞吐间取舍，不能只报一个“速度”。

注意三件事不是同一个概念：

1. FlashAttention 分块：在一次注意力计算内部安排数据和归一化。
2. Chunked prefill：把一个请求的 prompt 计算拆成多个调度单元。
3. Prefill/decode 分离部署：把两个阶段放到不同的执行资源。

这里的在线 Softmax 代码只涉及第 1 种算法思想；小调度器没有实现第 2、3 种。后续架构章节再讲 encoder/decoder 时，也不能把它们与服务端 P/D 分离混称。

## P15.14 TTFT、TPOT、吞吐：用时间戳而不是印象

本章固定采用**客户端可观察时间**：请求到达时间为 a，输出 token 接收时间依次为 t₁…tₙ。不同工具可能采用不同统计口径，比较前先写清楚。

```text
TTFT = t₁ - a                         首 token 等待
TPOT = (tₙ - t₁) / (n - 1)，n>1       后续每 token 平均间隔
E2E  = tₙ - a                         整个请求耗时
输出吞吐 = 观察窗口内输出 token 数 / 窗口秒数
```

TTFT 可以包含排队、prefill、采样与网络等延迟，不等于纯 prefill kernel 时间。TPOT 这里排除了第一 token 的等待。只有一个输出 token 时，没有后续间隔，所以脚本返回 `None`，不是除以零，也不是假装 TPOT=0。

再做一组**与上一节不同的人造时间线**：

| 请求 | 到达时刻（ms） | 输出 token 时刻（ms） | TTFT | TPOT | E2E |
| --- | --- | --- | --- | --- | --- |
| A | 0 | 100、140、190 | 100 ms | (190−100)/2=45 ms | 190 ms |
| B | 50 | 150、210 | 100 ms | (210−150)/1=60 ms | 160 ms |

观察窗口明确取 0–210 ms，两个请求一共产出 5 个 token，因此输出吞吐为 `5/0.210≈23.809524 tokens/s`。不能用 A 的 TPOT 倒数代表两请求总吞吐，也不能把两请求 E2E 相加当成并行服务的总墙钟时间。

“平均 TPOT”也要说清楚权重：

- 先算每请求 TPOT，再等权平均：`(45+60)/2=52.5 ms`。
- 把所有后续 token 间隔放一起平均：`(90+60)/3=50 ms`。

两者都可有定义，但不能用同一个标签不加说明。真实服务还应报告分位数、并发、错误率和输出长度；两条请求不足以说明线上长尾表现。

## P15.16 GPU 选修：先确认后端，不先晒跑分

**本批 GPU kernel 未运行，未测 GPU 显存、时延或吞吐。** CPU SDPA 检查通过不代表执行了 CUDA FlashAttention。

如果你已经有兼容的 GPU、驱动与官方 CUDA 版 PyTorch，可以单独尝试：

```bash
python code/16_attention_systems.py --gpu-sdpa
```

不要为这一章把现有 CPU 环境强行替换掉；GPU 环境的安装要按官方硬件/驱动要求单独配置。脚本会打印实际 PyTorch、CUDA、设备、dtype 和形状，并在缺少依赖或 CUDA 时明确 `SKIP`。本批实际运行这个开关得到：

```text
SKIP GPU SDPA: torch=2.14.1+cpu, CUDA unavailable; GPU kernel not run.
```

选修 smoke 的 Q/K/V 各为 `[1,1,8,16]`、float16；三者数据本身共 768 字节，但运行时上下文、工作区和 profiler 远不止这点，不能把 768 字节写成显存需求。它不下载模型，不承诺耗时或 GPU 总显存上限。

其核心调用明确限定后端：

```python
with sdpa_kernel(backends=[SDPBackend.FLASH_ATTENTION]):
    actual = torch.nn.functional.scaled_dot_product_attention(
        q, k, v, dropout_p=0.0, is_causal=True)
```

这里 Q/K 等长，才使用简单的 `is_causal=True`；带缓存偏移的矩形 mask 不应不加分析地照抄。函数的 dropout 参数明确设为 0，不依赖外部模型的 eval 状态。脚本记录 profiler 中实际出现的 attention/flash 事件，再与本章 CPU 数值参考比较；“调用了 SDPA”本身不能证明走了期望后端。[PyTorch 固定源码 v2.5.1：SDPA 后端选择接口](https://github.com/pytorch/pytorch/blob/v2.5.1/torch/nn/attention/__init__.py)

此固定源码链接用于接口背景，不是安装建议。本批另检查了实际 torch 2.14.1 的 `sdpa_kernel` 和 `SDPBackend.FLASH_ATTENTION` 可导入，但无 GPU，因此没有验证其 GPU 支持条件。后端不支持或运行失败时会报告 skip/失败原因，不会悄悄退回数学后端然后宣称 GPU Flash 成功。

要做真正的性能对比，还需要另外安排可复现基准：

1. 固定模型 revision、tokenizer、dtype、采样策略，记录权重与 KV 是否量化。
2. 固定 prompt/输出 token 长度分布、请求到达方式、并发以及前缀命中率；冷缓存与热缓存分开。
3. 先预热，再重复多轮；GPU kernel 计时使用同步或正确的 CUDA event，避免只测到提交任务的时间。
4. 同时报客户端 TTFT、TPOT、E2E、输出吞吐与失败请求；不能拿输入 token 吞吐冒充输出吞吐。
5. 显存分别记录模型基线、KV payload、峰值 allocated/reserved 和工作区；重置峰值统计的时机要相同。
6. 改一个因素再比，并核验 profiler 实际后端；保存硬件、软件版本和命令。微型 attention smoke 不能替代端到端服务基准。

这是选修实验的记录清单，**不是本批已经跑出的服务性能报告**。

## P15.17 自测题与参考答案

1. FlashAttention 为什么不等于把稠密 attention 改成 O(Nd)？与 GQA 分别改了什么？
2. N 从 4096 变为 8192，单头一张 2 字节 score 矩阵从多少 MiB 变成多少？
3. 手算例子第二块到来时，alpha、ell、acc、最终输出各是多少？若平均两块各自均值，会得到多少？
4. 第一块全 mask，后块才出现合法 key，该怎样初始化？若整行全 mask，本 API 输出什么？
5. b=4、长度 9 的无共享请求分配几个块、几个空槽？块表 `[9,2,7]` 中位置 7 对应哪里？
6. b=2 时 A/B 共享 `[10,20,30]`，B 追加 40 后，逻辑总长度与物理载荷数分别是多少？为什么只复制尾块？
7. 前缀文本“看起来意思一样”，能直接共享 KV 吗？这个模拟器会自动核验文本兼容性吗？
8. 连续 batch 的例子里 C 在 10 ms 就绪，为什么第一 token 是 30 ms，而不是 20 ms？这个 20 ms 等待能否叫真实端到端 TTFT？
9. 到达 0、输出时刻 `[100,140,190]` 的 TTFT、TPOT、E2E 各是多少？只输出一个 token 时 TPOT 是什么？
10. full/block 一致，且 CPU SDPA 通过，能否说明实现了生产 FlashAttention，并证明线上请求更快？

参考答案：

1. 它保留全部合法 QK 配对，标准稠密算术量仍为 O(N²d)，重点是计算组织与 IO。GQA 改变 KV 头共享方式，属于模型表示的改变。
2. 32 MiB → 128 MiB，增长 4 倍；这只是单张矩阵，不是完整模型峰值。
3. alpha=0.5，ell=1.75，acc=10.5，输出=6。错误的块均值平均是 17/3，约 5.6667。
4. 空块跳过，保持 ell=0；首个合法块用 alpha=0。整行无合法 key 返回全零，这是明确约定，不是正常概率分布。
5. 3 块、12 槽位、3 个空槽。位置 7 的逻辑块号 `7//4=1`、偏移 `7%4=3`，物理块号为 2。
6. 逻辑总长度 3+4=7，物理载荷数 2+1+2=5。满的前缀块继续共享；只要写入仍共享的未满尾块，才需要 COW。
7. 不能；要相同 token 前缀和兼容的模型/位置等计算环境。模拟器不检查文本或模型身份，调用者必须先保证前提。
8. 10–20 ms 两槽仍被 A/B 占用，C 到 20 ms 才开始一轮，30 ms 才产出。这里未包括 prompt prefill、网络等，不是端到端 TTFT。
9. 100 ms、45 ms、190 ms。只有一个 token 时没有后续间隔，TPOT 返回 None。
10. 不能。还要独立数值参考、GPU 后端证据，以及同硬件、同工作负载的性能测量。本章只完成教学 CPU 实验。
