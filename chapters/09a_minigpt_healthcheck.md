# 综合实验（P27）：给自己的 miniGPT 做体检 {#p27-healthcheck}

换了轮胎的自行车，能在院子里骑一圈，不代表刹车、转向、载重都没有问题。同样，模型能输出一句话，也不代表位置没有错、未来没有泄漏、第二个请求没有混进第一个请求的缓存。

前面我们逐件学习了 KV cache、RoPE、RMSNorm、SwiGLU、GQA、MoE 和可选 MTP。本章不再发明一种新架构，而是把已有零件放到同一张检查单上：**哪个东西应该保持相同，哪个允许改变，出现差异后应该先查哪里？**

配套 [code/28_minigpt_healthcheck.py](../code/28_minigpt_healthcheck.py)，测试为 `tests/test_minigpt_healthcheck.py`。它直接导入前面章节的模型和缓存函数，不复制第七份 Transformer，也不改动历史基线 [Baby-GPT](../code/07_baby_gpt.py)。默认一条命令覆盖 S0–S5；`--mtp` 打开 S6 旁路。

阅读前建议完成 [第 8 章 Baby-GPT](#任务边界与运行)、[P11 KV cache](#p11.1-重算发生在哪里)、[RoPE](#p12-rope)、[现代 Block](#p13-modern-block)、[GQA](#p14-grouped-kv)、[MoE](#p18-moe)。MTP 部分可结合 [P23](#p23-mtp) 选读。如果忘了某个名词，先看 [附录](#p28-reference)，不用把所有框架重新安装一遍。

> 体检类比的边界：软件检查不是医学诊断。“通过”只表示列出的输入、性质和运行环境没有发现问题，不是证明所有输入都正确。反例可以推翻一个断言；几个成功例子不能证明无限多个情况。

## P27.1 先分清三种“相同”

做实验最容易犯的错误，不是写错一个公式，而是比较了不应该相同的东西。

| 比较对象 | 期待什么 | 为什么 |
| --- | --- | --- |
| 同模型、同权重、同 token，完整前向与缓存前向 | logits 在规定容差内相同 | 缓存只是复用以前算过的 K/V |
| 同配置、同词表、保存前与重新加载后 | 权重完全相同；本实验输出完全相同 | 序列化不应该悄悄改变模型 |
| 把 LayerNorm 换成 RMSNorm | 输出通常不同 | 计算本来就变了，应检查公式与受控差异 |
| 把 MHA 的 KV 头减半 | 缓存载荷下降；输出不必相同 | 参数结构与信息共享方式变了 |
| 固定随机种子，重新创建两种架构 | 不能直接要求所有对应权重相同 | 新增模块会消耗随机数，初始化顺序可能改变 |
| 更长输出与更短输出 | 不一定更正确 | 计算预算、语言长度和答案质量是不同指标 |

**数值等价**是在相同数学任务上比较两种计算路径；**消融实验**是只改变一个明确因素，观察变化；**模型质量评测**则需要有意义的数据、任务与独立检查器。三者不能互相代替。

本章输出的 loss 是随机模型在两行合成 token 上的交叉熵或含 MoE 辅助项的训练目标。它能帮助发现 NaN、错形状和断开的梯度，不能用来宣布 S4 比 S3 更聪明。甚至 S5 的总 loss 和 S4 也不完全是同一种量：S5 默认还加了负载辅助项。

## P27.2 S0–S6：升级路线不是权重转换说明书

阶段表示“这一章增加了什么”，不表示所有阶段都能直接读同一个 checkpoint。

| 阶段 | 真正调用的旧实验 | 本次主要变化 | 体检重点 |
| --- | --- | --- | --- |
| S0 | `07_baby_gpt.py` | 绝对位置、LayerNorm、GELU、MHA 基线 | 前后向、因果性、保存加载 |
| S1 | `12_kv_cache.py` | 给同一个 S0 对象增加缓存计算路径 | 完整／分块 logits；请求边界 |
| S2 | `13_rope.py` | 用 RoPE 替代绝对位置表 | 旋转手算；缓存偏移；因果性 |
| S3 | `14_modern_block.py` | 现代归一化与 FFN | 公式、有限梯度、分两步消融 |
| S4 | `15_grouped_kv.py` | 分组 KV 头 | 头映射；实际缓存载荷 |
| S5 | `19_moe.py` | 将稠密 FFN 换成教学 MoE | 路由计数；梯度；缓存等价 |
| S6，可选 | `24_reasoning_mtp.py` | 加独立未来预测 head | 标签对齐；辅助梯度；贪心验证 |

S1 不是“另一份初始化恰好相同的 S0”：脚本把**同一个模型对象**分别交给普通前向和缓存前向。这样排除了“看起来比较缓存，实际比较两组权重”的错误。

S2–S5 是分别建立的教学阶段，不宣称已经转换、继承或训练好上一阶段的权重。S3 默认还涉及 bias 策略，所以不能把 S2 与默认 S3 的所有差异都归因于 RMSNorm；真正的单变量控制组在 P27.7 单独建立。

S6 先用独立种子 271 初始化，再显式复制种子 270 的 S5 所有已有状态，保留新建的两个旁路 head。这样，删掉复制步骤时主干权重确实不同，不会被相同种子的巧合掩盖。因此没有训练更新之前，S5 与 S6 的**普通主 head 输出**相同；S6 的辅助目标不同。MTP 并不自动修改普通生成算法，也不是生产 DeepSeek 的顺序 MTP 或 DSpark 实现。[DeepSeek-V3 报告 v2，MTP](https://arxiv.org/abs/2412.19437v2)

## P27.3 一条命令，从输入到报告

### 运行入口与失败含义

在仓库根目录、已安装 `requirements.txt` 的 Python 环境中运行：

```bash
OMP_NUM_THREADS=1 python code/28_minigpt_healthcheck.py
```

加上可选 MTP 检查：

```bash
OMP_NUM_THREADS=1 python code/28_minigpt_healthcheck.py --mtp
```

需要保存可比较的机器可读报告时：

```bash
OMP_NUM_THREADS=1 python code/28_minigpt_healthcheck.py --mtp --json > healthcheck.json
python -m unittest discover -s tests -p 'test_minigpt_healthcheck.py' -v
```

`--json` 只改变输出格式，不跳过任何检查；每个缓存阶段的 `chunk_checks` 记录实际运行的四种分块及各自误差、字节数，汇总误差取其中最大值。默认路径不下载模型、不访问外部服务、不使用 GPU。脚本把 CPU 线程设为 1，主线随机种子为 270，使用 float32；S6 独立初始化使用 271，随后复制 S5 主干。版本、设备、线程、种子、形状和容差写进报告，不只打印一个绿色 PASS。

缺少 PyTorch 时，CLI 给出安装提示并以状态码 2 退出，明确写 `NOT RUN, not passed`；作为模块导入时仍抛出真实依赖错误。测试可以因没有受支持 Torch 而跳过数值路径，但**跳过不等于通过**。其他导入错误、错误实现崩溃或输出 NaN 不能被包装成“负例成功”。

### 固定输入，先别谈中文质量

本次使用词表大小 V=17 的合成整数 ID，不使用三首诗的字符词表，也没有把整数大小当成语义。每行是一条独立合成文档，不做 padding、跨文档 packing 或聊天模板。

| 行 | 输入 x，8 个 token | 标签 y，8 个 token |
| --- | --- | --- |
| 0 | 1, 2, 3, 2, 6, 7, 4, 8 | 2, 3, 2, 6, 7, 4, 8, 9 |
| 1 | 4, 0, 2, 1, 4, 3, 8, 6 | 0, 2, 1, 4, 3, 8, 6, 5 |

代码先写出 9 个 token 的流，再取 `stream[:, :-1]` 和 `stream[:, 1:]`。最后一个标签来自第九个 token，**不是把窗口开头卷回来**。这能验证 next-token 的位置关系，但不能证明真实训练集的去重、许可与切分已经做好。

统一小配置为 B=2、T=8、D=16、Hq=4、每头 d=4、层数 L=2、上下文上限 16。GQA 使用 Hkv=2；MoE 每层 4 个路由专家、top-k=2、专家宽度 7，另有 1 个宽度 5 的共享专家。

### 脚本到底做了什么

顺着 `run_healthcheck` 阅读，比一次看完所有模型源代码容易：

1. `make_stages` 导入旧课例并建立小模型；S0/S1 共用对象，S6 保持 S5 主干权重。
2. `fixture` 产生同一组 x/y；`finite_backward` 检查目标有限、主干与主 head 有梯度，并至少有非零梯度。不执行 optimizer 更新。
3. `causal_error` 只改未来输入，检查所有过去位置的 logits。
4. `checkpoint_error` 写入内存文件、严格读回，并逐个核对状态张量和输出。
5. 有缓存的阶段分别运行 `[3,1,4]`、八次 `[1]`、`[8]` 和 `[7,1]` 四种分块，检查缓存长度与载荷；再检查请求重置与容量溢出。
6. `component_oracles` 用独立手算答案检查旋转、归一化、门控、分组和路由；`compatibility_checks` 验证不兼容加载真的被拒绝。
7. 运行真实控制组、三类坏行为；选修 MTP 再做标签、梯度与贪心对照。
8. 用同一个 S0 权重和固定 token 重放，记录普通／缓存 CPU 前向的计时分布。

这里的 backward 是**梯度 smoke**，不是训练完成。参数没有更新，checkpoint 也不包含 optimizer 或 RNG 状态。想验证中断后能否继续同一条训练轨迹，需要回到训练流水线章节，保存更完整的恢复状态。

正常实现从不触发某道防线，不代表防线已经被测试。这里另外包装真实计算，逐一制造下列坏行为；正常体检必须拒绝，删掉对应检查的源码变异则会放过它，其他检查保持原样。

| 注入的坏行为 | 应报警的位置 |
| --- | --- |
| 处理了 8 个 token，返回的缓存却声称长度为 9 | 缓存长度与已消耗前缀比较 |
| 长度 16 后再输入 1 个，静默丢掉最老 K/V | 容量溢出必须被拒绝 |
| 新请求传入 `None`，实现却沿用旧的 3-token 历史 | 新请求输出与独立完整前向比较 |
| 路由 logits 不变，但负载账本从 32 写成 33 | MoE 请求总数核对 |
| loss 加上 NaN 常量，梯度仍然有限非零 | 反向之前检查 loss 有限 |

最后一行尤其容易误判：常量加法不改变对参数的导数，因此“梯度有限”不能代替“目标有限”。

## P27.4 一张张量账本，先抓形状再抓数值

| 张量或量 | S0/S1 | S2/S3 | S4/S5/S6 |
| --- | --- | --- | --- |
| 输入 ID | [2,8] | [2,8] | [2,8] |
| 完整 logits | [2,8,17] | [2,8,17] | [2,8,17] |
| 单层缓存 K 或 V | [2,4,8,4] | [2,4,8,4] | [2,2,8,4] |
| 绝对位置表 | 有 | 无 | 无 |
| 两层 K+V 的 float32 载荷 | S0 不建缓存；S1 为 4096 字节 | 4096 字节 | 2048 字节 |

缓存公式是：

$$
\text{bytes}=2\times L\times B\times H_{kv}\times T\times d\times s.
$$

第一个 2 是 K 和 V 两份，s 是每元素字节数。MHA 时 Hkv=Hq=4；因此 `2×2×2×4×8×4×4=4096`。GQA 把 Hkv 改为 2，结果为 2048。这是从实际缓存张量 `numel×element_size` 求和后，再与独立整数账本对照的值。 测试还把同样形状的模型改为 float64，逐个确认缓存张量每元素 8 字节：MHA 为 8192 字节，GQA 为 4096 字节。若把元素大小写死为 4，这个独立 dtype 对照会失败。

这里**不是测出来的进程内存，更不是显存峰值**。模型权重、注意力分数、临时复制、Python 对象、分配器缓存都没计入。S4 计算注意力时还会临时展开共享 K/V；存储的缓存必须保留 Hkv 头，不能把展开后的 Hq 份偷偷存回去。

Hq=4、Hkv=2 时，查询头的映射是 `[0,0,1,1]`。给两个 KV 头分别填入 `[10,11]` 和 `[20,21]`，只放一个可见 key，四个查询头输出应为：

| 查询头 | 使用的 KV 头 | 结果 |
| --- | --- | --- |
| 0 | 0 | [10,11] |
| 1 | 0 | [10,11] |
| 2 | 1 | [20,21] |
| 3 | 1 | [20,21] |

只有一个 key 时权重必为 1，因而此例不用依赖另一份 softmax 实现，就能抓住错误的 `[0,1,0,1]` 映射。GQA 原论文还讨论了从 MHA checkpoint 初始化并继续训练的路线；“可以 uptraining”不能缩写成“直接改配置，函数完全不变”。[GQA v1](https://arxiv.org/abs/2305.13245v1)

## P27.5 两个不变量：缓存等价与未来不可见

### 不变量 A：换计算顺序，不换模型含义

对同一组权重 θ 和输入 x，完整计算得到 `model(x)`。分块计算则先喂 3 个 token，再喂 1 个，最后喂 4 个，把各段 logits 按时间拼接。要求每个位置都对齐，不只比较最后一个生成 token。

$$
\left|z_{cache}-z_{full}\right|\leq atol+rtol\left|z_{full}\right|.
$$

本章 float32 使用 `atol=3e-6`、`rtol=1e-5`，同时记录最大绝对误差。不同批形、矩阵乘法路径与累加顺序会带来末位浮点差异，所以不能把所有缓存比较写成逐 bit 相等；也不能随意把容差放宽到“看起来差不多”。

为什么跑四种分块？单 token decode 擅长暴露位置偏移错误，多 token chunk 擅长暴露矩形 mask 错误，整段前向则给出没有历史缓存的边界。如果只测 `T=1` 或只测一次完整 prefill，某些错误永远不触发。 测试另外只破坏第一块或中间块的输出，保留正确 K/V 和最后一块，确认完整比较会报警；把检查器改成只看最后一块的真实源码变异则会漏过，因此该错误不能再被正常输出样本掩盖。

对照对象也必须锁住：若把完整前向换成“缓存路径一次喂完”，两边可能共享同一个错误。测试让缓存路径的每块 logits 都加 0.25，四种分块都应被真正的完整前向抓住；缓存路径与自己比较却会漏掉。另一个测试只把第一块乘 1.5，包括整段 `[8]` 在内也都应报警。这里没有改 K/V，错误只在返回的 logits，不能依靠后续缓存崩溃碰巧抓住它。

最小实现轮廓如下，真正模型仍来自旧章节：

```python
cache, pieces = None, []
for chunk in chunks:
    logits, cache = cached_forward(model, chunk, cache)
    pieces.append(logits)
actual = torch.cat(pieces, dim=1)
check_close(actual, model(tokens)[0])
```

必须先 `eval()`。当前小模型没有 dropout，但固定推理模式是接口契约；不能依靠“这次碰巧没有随机层”。缓存也不能在权重更新、dtype 改变后继续使用。

### 不变量 B：改变未来，不改过去

先用切点 3 举例：把输入前三个位置保留，后五个位置全部换成别的合法 ID，再比较前三个位置的全部 logits。因果 decoder 的过去输出不应依赖未来输入。实际 CLI 会遍历 1–7 的全部切点，JSON 的 `causal_checks` 逐项记录误差，`causal_error` 是其中的最大值；不能只抽查切点 3。

这里检查的是**干预**，不是“注意力图看起来是三角形”：如果程序画出一个正确的 mask，却没有真的把它用进计算，干预测试仍会失败。

为什么遍历所有切点？测试只让最后一层的位置 5 偷看位置 6。切点 3 看不见这次泄漏，切点 6 才会暴露它；CLI 必须在进入缓存比较之前就因未来依赖报警。

数值测试进一步遍历每一个切点，并用 float64 检查。稠密阶段要求过去输出精确不变；MoE 给出极小的 `1e-12` 绝对容差、相对容差 0，因为不同未来路由可能改变专家 GEMM 的行分组和末位累加。这个容差不是允许跨 token 交流：正常路由只依赖当前 token 的隐藏状态，不应把未来 token 的内容带回过去。

因果性通过也不能说明 padding mask、跨文档隔离、左右 padding 或 ragged batch 都正确。这些没有在本次输入里出现，必须另外设计样本。

## P27.6 Checkpoint：箱子装得下，不代表零件匹配

`state_dict` 是命名张量集合，能告诉我们“这一块矩阵有多大”。它不一定告诉我们 RoPE base、token ID 的含义、推理模板或一个数值参数的语义。

例如，17×16 的 embedding 矩阵可以原样加载，但如果词表把 ID 0 和 ID 1 的意义交换，整个模型已经变了。又如 RoPE base 从 10000 改成 20000，参数矩阵形状完全相同，位置计算却不同。`strict=True` 能抓住缺键、多键与形状错误，不能单独解决这些问题。

本章使用一个小型、保守的本地格式：

| 保存内容 | 防什么错误 |
| --- | --- |
| 格式版本与架构 family | 把别的文件或阶段当成这个模型 |
| 完整 dataclass 配置 | 漏记 RoPE base、头数、epsilon、专家参数 |
| 按 ID 顺序排列的合成词表 | 相同词表大小，不同 token 含义 |
| MTP depth | 忘了额外 head 的数量 |
| float32／float64 dtype | 悄悄转换精度 |
| 严格 state_dict | 缺失、多余或错形状张量 |

加载端必须明确传入**期望的阶段、配置、词表与 depth**，先比较语义元数据，再逐键检查目标 dtype，最后严格加载张量。仅检查浮点张量不够：整数、布尔或复数张量也可能被加载接口悄悄转换成浮点权重；参数与 buffer 都必须匹配对应目标张量的 dtype。文件不能任意指定一个 Python 模块让加载器导入。该格式只服务本书工厂建立的教学模型，不支持给模块随手 monkey-patch 后的任意运行时结构。

| 尝试 | 本章结果 | 理由 |
| --- | --- | --- |
| S0 存，S1 读；配置、词表相同 | 允许，并逐张量核对 | 实际是同一种 BabyGPT 架构 |
| 任意阶段同配置、同词表、同 depth 往返 | 允许 | 对应模型按原规则重建 |
| S0 文件当成 S2 | 拒绝 | 绝对位置与 RoPE 不同 |
| 只改 RoPE base，矩阵形状不变 | 拒绝 | 配置语义不同 |
| 只把词表顺序倒过来 | 拒绝 | ID 的含义不同 |
| GQA 的 Hkv 从 2 改为 1 | 拒绝 | KV 投影与缓存形状改变 |
| S4 文件直接读成 S5 | 拒绝 | 稠密 FFN 与专家结构不同 |
| S6 depth=2 文件按 depth=0 读取 | 拒绝 | 辅助 head 集合不同 |

S3 特殊设置可以在数学上退化成之前的结构，S6 depth=0 也可以与 S5 主干相同；本章加载器仍采取保守阶段边界，**没有声称所有理论上可转换的情况都已实现转换器**。需要转换时，应另写显式映射，记录丢弃、初始化和需要重新训练的部分，再独立验证。

保存文件不包含请求缓存。缓存是特定模型对象、权重版本和 token 历史的临时产物；即使新模型加载了相同权重，也不应把旧对象的缓存直接交给它。正确顺序是加载模型、`eval()`、对当前请求重新 prefill。

保存端拒绝本实验不支持的 bf16 与含 NaN 的状态，加载端拒绝 envelope 多出的键。相应测试先检查正常路径，再观察坏数据确实被拒绝；移除对应守卫的源码变异会让坏文件被写出或被接受。

逐张量核对也不能被“本次输出相同”替代：S0 的 mask 是 16×16，本次 T=8 只用左上角。测试改变 `[15,15]`，本次 logits 仍完全相同，但 checkpoint 的状态已经不忠实，往返检查必须报警。兼容性测试还区分拒绝原因：一个文件若先因不支持的 dtype 被拒绝，不能把这次异常算作“架构语义不兼容已验证”。

只加载自己生成或明确可信的文件。测试使用没有自定义还原方法、没有执行副作用的普通字典子类，确认限制型反序列化会拒绝未允许的对象，而不是用危险载荷演示风险。代码使用 CPU 映射与 `weights_only=True`，这是收窄反序列化行为，不是“网上任何文件都安全”的承诺。[PyTorch 2.14 的 torch.load 文档](https://docs.pytorch.org/docs/2.14/generated/torch.load.html)

## P27.7 单变量报告：一项改动，不是只写一句话

如果 A 使用 LayerNorm+GELU+bias，B 使用 RMSNorm+SwiGLU+无 bias，loss 变了，我们不能知道是哪项起作用。公平比较要把“没改的东西”真正固定下来，不只在论文标题里写 ablation。

本章复用 P13 的三个控制组，所有组都关闭 norm/FFN bias：

| 控制组 | 归一化 | FFN | 中间宽度 | 每层 FFN 参数 | 总参数 |
| --- | --- | --- | --- | --- | --- |
| A | LayerNorm | GELU | 64 | 2048 | 6768 |
| B | RMSNorm | GELU | 64 | 2048 | 6768 |
| C | RMSNorm | SwiGLU | 43 | 2064 | 6800 |

A→B 只换归一化，复制并核对所有非 norm 状态。B→C 只换 FFN 家族与预算匹配宽度，复制并核对所有非 FFN 状态。脚本分别确认 14 个和 15 个不该改变的张量完全相同；输入、标签、dtype、设备和检查路径也相同。

为什么 C 不是正好 2048？无 bias 时，GELU 两个矩阵的参数为 `2Dm`，SwiGLU 三个矩阵的参数为 `3Dn`。D=16、m=64 时，理想 n 为 42 又 2/3；宽度必须是整数，选择 43 后为 `3×16×43=2064`，每层多 16 个，两层总共多 32 个。

所以这个实验应叫**FFN 家族加近似匹配宽度的消融**，不能叫“仅改变激活函数，其他完全不变”。RMSNorm 不做减均值，而 SwiGLU 多了一条门控乘积；它们的原始定义分别见 [RMSNorm v1](https://arxiv.org/abs/1910.07467v1) 与 [GLU Variants v1](https://arxiv.org/abs/2002.05202v1)。

### 再用两个手算检查，防止“大家一起错”

完整前向与缓存前向可能共用同一个错误的 RMSNorm，因此二者相等还不够。脚本还用不会调用被测公式的字面答案：

- RMSNorm：x=[1,3]，epsilon=0.5，gamma=[1,1]。均方为 5，所以结果为 `[1/√5.5, 3/√5.5]`。
- SwiGLU：沿用 P13 的 gate=[-1,2]、up=[3,4]、down=单位矩阵。结果为 `[-3/(1+e), 8/(1+exp(-2))]`，约 `[-0.806824,7.046377]`。
- RoPE：把 `[3,4]` 旋转 π/2，应得到 `[-4,3]`，长度仍为 5。这里 θ=1 的二维特例足以发现旋转符号写反；不是完整的长上下文能力测试。[RoFormer v1](https://arxiv.org/abs/2104.09864v1)

报告还列每组随机初始 loss 和缓存误差，但本章不更新这些模型，不把三个数排成质量排行榜。下一步若做训练消融，需固定训练预算、独立验证集、多个随机种子与优化器条件，再报告均值、波动和负结果。参数接近并不意味着 FLOPs、吞吐或训练难度相同。

## P27.8 故意弄坏它：检查器必须真的会报警

一个永远回答“没问题”的体检程序没有价值。本章的三个负例都运行真实模型计算，得到**有限而错误的 logits**，再由正常的数值比较发现问题。没有直接打印预设 `caught=True` 来替代执行。

### 负例一：矩形 mask 不能直接 tril

缓存里已有 P=3 个位置，新来 C=2 个查询。完整 key 长度为 5，查询的绝对位置是 3 和 4。

| 查询 | key 0 | key 1 | key 2 | key 3 | key 4 |
| --- | --- | --- | --- | --- | --- |
| 位置 3，正确 | 看见 | 看见 | 看见 | 看见 | 遮住 |
| 位置 4，正确 | 看见 | 看见 | 看见 | 看见 | 看见 |
| 第 0 行，错误 tril | 看见 | 遮住 | 遮住 | 遮住 | 遮住 |
| 第 1 行，错误 tril | 看见 | 看见 | 遮住 | 遮住 | 遮住 |

正确判断是 `key_position <= query_position`，不是把局部查询行号当成绝对位置。这个错误没有泄漏未来，却丢掉了本来可见的过去，因此**只测因果性抓不到它**，必须与同权重完整前向比较。

用未归一化权重 `[1,2,3,4,5]` 和 value `[10,20,30,40,50]` 手算：正确两行输出为 30 和 110/3；错误 tril 为 10 和 50/3。一个 mask 的局部行号偏移，就把计算换了问题。

CLI 在内存里从 S1 的真实函数源码生成变异版本，只替换这一行 mask，不修改磁盘上的旧课例。源码锚点如果找不到或出现多次，直接失败，不能悄悄跳过。

### 负例二：每个块都从位置 0 开始

第一块 `[1,2,3]` 使用位置 0、1、2。第二块的第一个 token 应使用位置 3，而不是又回到位置 0。

S1 负例把 `arange(offset, offset+T)` 改成 `arange(T)`，只破坏绝对位置，不同时破坏 mask。第一块仍然正常，因此只测 prefill 看不出问题；第二块对照会失败。S2 的 RoPE 也必须使用连续位置，且旧 K 不应被再次旋转，相关数学与缓存契约仍由 P12 的原测试覆盖。

定位时要问：是新 Q/K 的位置错了，还是旧 K 被二次旋转？是模型要求的绝对位置偏移，还是已经采用另一个明确设计的位置方案？不能只看到 cache error 就笼统怪罪精度。

### 负例三：第二个用户接上了第一个用户的历史

请求 A 的前三个 token 已经产生缓存。请求 B 应从空缓存开始，负例却把 A 的缓存传给 B 的完整输入。

这一次模型对象相同、权重没变、batch 形状也相同，所以 owner 与版本检查可能全部通过。程序确实在计算一个合法的更长序列，只是**不是用户想要的那个请求**。

正确答案是 B 单独的完整前向；污染答案是“A 前缀+B”中 B 那些位置的输出。两者不同。缓存对象无法凭空猜到调用者的请求意图，服务层必须为每个独立请求明确传入 `None` 或自己的独立状态。

本次负例没有伪造签名，也没有禁用缓存防护。它展示防护的边界：校验对象与权重，不等于自动识别请求历史。真实系统还要考虑租户隔离、前缀缓存授权、并发取消和缓存回收，本章没有实现这些服务功能。

### 本机实际结果怎么读

2026-10-20，Python 3.12.14、PyTorch 2.14.1+cpu、单线程、seed=270，按上述固定输入运行：

| 负例 | 最大绝对 logit 差异，约 | 判定 |
| --- | --- | --- |
| wrong_mask | 0.490929 | 同权重缓存等价检查抓住 |
| wrong_position | 1.453250 | 同权重缓存等价检查抓住 |
| cache_pollution | 1.488388 | 新请求完整前向对照抓住 |

这些数是本次 CPU 浮点实测，不保证跨平台最后几位相同；“显著超出容差且仍为有限输出”才是测试契约。测试还反向验证：如果变异器根本没改源码，负例检查必须失败；如果缺依赖而抛异常，也必须继续报错，不能算成功捕获数学错误。 数值反例必须产生有限的错误输出；dtype、owner、反序列化与梯度守卫则检查具体拒绝原因，并独立观察删掉守卫后被放过的坏状态。这两类证据不混算。

此外，测试对真实模型取消因果 mask，对旋转符号、RMS 统计、门控、GQA 映射、checkpoint 元数据检查、消融权重与 MTP 标签做实际行为变异。作用是验证这些 oracle 真能区分好坏，不是增加几个永远为真的断言。

## P27.9 MoE 与选修 MTP：不能只看一行 loss

### MoE 的负载账本

两行、每行 8 个 token，共 N=16；每个 token 选择 2 个路由专家，因此每层请求分配数总和必须为 `N×k=32`，不是 16。共享专家总是运行，不记在这 32 次路由分配里。

本次 S5 两层的请求负载为 `[7,8,8,9]` 与 `[4,9,9,10]`。每层都加起来为 32，但并不完全均衡。这个数字说明路由确实在工作，不表示专家已经学会了分工，更不表示单机 MoE 更快。[DeepSeekMoE v1](https://arxiv.org/abs/2401.06066v1)

独立手算例子使用三行路由概率 `[.4,.3,.2,.1]`、`[.1,.2,.3,.4]`、`[.4,.4,.1,.1]`。top-2 的选择应为 `[0,1]`、`[3,2]`、`[0,1]`，对应权重 `[4/7,3/7]`、`[4/7,3/7]`、`[1/2,1/2]`；负载为 `[2,2,1,1]`。平局按较小专家 ID 先选，答案可直接逐行核对。

测试再把 router 权重全部置零，强制所有 token 选择专家 0、1，负载应为 `[16,16,0,0]`。未被选中的专家梯度可以是 `None`，这不是自动判错的理由；但主干、主 head 与实际参与计算的路径不能整体断掉。有限梯度检查要理解稀疏计算，不能对所有参数一刀切要求非空。

主线 MoE 不按每个 chunk 的容量丢弃 token。若一次完整前向和分三块前向采用不同的丢弃结果，即使 attention cache 完全正确，最终 logits 也可能不同。容量策略是额外的计算语义，不是随手加一个性能开关。

### 打开 S6 后，多检查三件事

八个输入位置、两个额外 head，对应 horizon=1、2、3。每行有效标签数分别为 7、6、5，两行合计 14、12、10。尾部没有未来标签的格子用 `-100` 忽略，而不是预测 token 0。

脚本用 Python 逐行、逐位置索引写出独立标签答案，再按 `logsumexp(logits)-正确类别logit` 手工汇总有效位置损失，与 MTP 的各 head CE 比较。合成目标为主 CE，加 0.2 倍额外 head 平均 CE，再加已经缩放过的 MoE 辅助项。之后检查旁路 head 收到有限非零梯度。测试通过真实 backward hook 分别制造全零／NaN 梯度，或仅 detach 主 head、旁路 head 的权重，验证有限 loss 不会掩盖断开的学习路径；同时保留其他正常路径，避免把无关崩溃当成守卫有效。

最后拿前两个 token 作 prompt，生成 7 个新 token：一边用最简单的**完整前缀重新计算**循环做 greedy，另一边用 S6 的 drafter 与缓存验证。二者生成的整个 token 序列必须相同，不能只比较长度或最后一位。

本机这组随机权重下，草稿提出 7 个 token，接受 3 个；目标模型调用 4 次、处理 12 个输入 token；drafter 调用 3 次、全前缀累计处理 15 个 token。这些是实际计数，不是耗时收益。减少目标调用的同时可能处理了更多被拒绝 token，还增加草稿成本。

本章只检验**贪心**规则保持，不实现随机投机采样的接受率校正，也没有证明语言答案正确。即使目标模型生成完全错误的句子，忠实保持它的 greedy 结果仍可能通过算法检查。

## P27.10 成本与性能：记账可以，外推不行

### 固定参数与缓存报告

本次小模型的稳定整数结果如下。它们是所选配置的参数计数，不是某个模型系列的宣传参数。

| 阶段 | 参数总数 | T=8 时缓存字节 |
| --- | --- | --- |
| S0 | 7264 | 不建缓存 |
| S1 | 7264 | 4096 |
| S2 | 7008 | 4096 |
| S3 | 6800 | 4096 |
| S4 | 6288 | 2048 |
| S5 | 5456 | 2048 |
| S6，depth=2 | 6000 | 2048 |

S5 比 S4 参数少，是因为这里故意选择了很窄的专家，并非“MoE 总参数一定更少”。S6 多出的 `2×17×16=544` 来自两个线性 head；普通主干 KV 不变。激活参数、参数总数、缓存字节、算子次数和运行时内存不是同一种指标。

本机各阶段缓存／完整前向误差远低于 `3e-6` 的绝对容差；实际通过条件仍联合使用上文的 `atol=3e-6`、`rtol=1e-5`，保存加载输出误差为 0。重新运行应看自己的报告与容差，不要把这组末位数值当成所有机器必须逐字匹配的截图。

### 同权重 CPU 时间小实验

计时只比较 S0 普通前向与 S1 缓存路径，使用同一模型、同一固定 token。参数如下：

- B=2、总 T=8，prompt 长度 3，之后重放 5 个固定 token。
- CPU 单线程，float32；预热 2 轮，正式重复 5 轮，交替先跑普通或缓存路径。
- 使用同步 CPU 的 `perf_counter`；没有 GPU 异步工作，不需要 CUDA synchronize。
- 分别记录 prompt forward 与后续每 token forward 的 min／median／max，单位毫秒。
- 不含 tokenizer、采样、网络、排队或 UI；不是服务端真实 TTFT／TPOT。

一次实测的普通／缓存 prompt 中位数约为 0.326／0.456 ms，后续每 token 前向中位数约为 0.357／0.509 ms。**这里缓存更慢**，并不推翻它减少重复计算的原理：短序列、小矩阵下，Python 检查、拼接缓存和函数开销可能占主导。这个样本不构成一般性能结论，报告里的范围比一个百分比更诚实。

CPU 模拟无法推出 GPU kernel、显存峰值、多请求吞吐或长上下文收益。若选做 GPU 基准，另建记录，至少写清设备型号、驱动／框架版本、dtype、模型与 tokenizer revision、B/T、输出长度、并发、实际后端、预热、同步位置、重复次数与波动。不要用本章的“无 GPU”结果填那张表的已测栏。

## P27.11 当体检失败，按症状缩小范围

| 现象 | 先查哪里 | 不要立刻做什么 |
| --- | --- | --- |
| 完整前向本身含 NaN | 输入范围、mask 全遮住、除零、dtype、loss | 先把容差放大 |
| 完整前向正常，第二块开始错 | position offset、矩形 mask、旧 K 是否重复旋转 | 重训模型碰运气 |
| 只在第二次请求出现差异 | `cache=None`、请求归属、权重版本 | 把缓存永久放模型全局变量 |
| 过去 logits 随未来 token 变化 | causal mask 是否真正参与计算；跨 token 路由操作 | 用一张热力图证明没有泄漏 |
| checkpoint 形状都对，输出却变了 | 词表顺序、RoPE base、norm epsilon、dtype、实际代码版本 | 关掉 strict 强行加载 |
| MoE 部分专家无梯度 | 是否真的被选中；统计负载；shared 路径 | 要求空专家凭空产生梯度 |
| 草稿验证输出不同 | 首个拒绝处、丢弃后缀、cache trim、pending token | 把相似文本当成正确等价 |
| 更少 KV 字节却更慢 | 临时展开、检查与 cat 成本、规模、计时边界 | 宣称压缩机制无用或一定加速 |

建议每次只缩小一个维度：先 B=1、T=1，再 T=2；先一层，再多层；先 dense，再 MoE；先 float64 手算，再回到实际 dtype。把首个出错位置保存下来，比抄十屏日志更有用。

修复之后，先运行能重现问题的最小测试，再跑整条 smoke 与全套回归。不要删除那个失败样本来让报表变绿。若错误来自上游版本变化，也要记录差异和新版本，不把旧结论原样挪过来。

## P27.13 自测：能解释失败，比记住 PASS 更重要

1. S0 和 S1 为什么必须用同一组权重？固定随机种子是否足够？
2. P=3、C=2 时，正确矩形 mask 的第一行应该看见几个 key？为什么直接 tril 错了却仍可能通过因果测试？
3. GQA 把本次缓存从 4096 字节降到 2048 字节，是否证明进程内存或 GPU 显存下降一半？
4. 两个 checkpoint 张量形状都相同，举两个仍可能不兼容的原因。
5. S3 的 C 组每层 FFN 比 A/B 多多少参数？这还能叫“只换激活函数”吗？
6. 同一个模型对象、同一组权重、相同 batch，为何仍可能发生请求缓存污染？
7. MoE 的 16 个 token、top-2，为何负载总数应为 32？空专家没有梯度一定是 bug 吗？
8. S6 horizon=3、两行各 8 个输入，为什么只有 10 个有效标签？贪心一致能证明随机采样分布一致吗？
9. 同权重缓存前向和完整前向都调用了错误的 RMSNorm，缓存等价测试能抓到吗？需要补什么？
10. 测试因缺 Torch 跳过、负例因导入失败退出、负例输出有限但偏离 oracle，哪一种才是本章想看到的负例证据？

### 参考答案

1. 缓存改变计算安排，不应同时改变模型；同一对象最直接。不同架构消耗随机数的顺序不同，仅种子相同不足以保证对应张量相同。
2. 看见 4 个。直接 tril 用的是局部行号；它可能只少看过去，没有看未来，故需要完整前向对照。
3. 不能。只核算 KV 张量载荷，不含权重、临时张量、分配器等。
4. 词表 ID 顺序、RoPE base、norm epsilon、执行语义等都可能不同。
5. 多 16 个。改了 FFN 家族和匹配宽度，不是 activation-only 对照。
6. 缓存的内容属于具体 token 历史。owner 相同不代表请求相同；新请求必须明确重置。
7. 每个 token 请求两个路由分支。空专家可能没有参与图，梯度为 `None` 合理，但要核对路由、主干和被用到的路径。
8. 每行只有前 5 个位置有第三个未来 token，故 5×2=10；不能推导随机采样分布保持。
9. 未必，两个路径可能一起错。补独立标量公式、字面手算答案及能被抓住的实际变异。
10. 只有最后一种。前两种应标未运行或失败，不能装成数学正确性证据。

## 本章小结 {#p27-summary}

miniGPT 的升级不是把开关越来越多地塞进第一份源码，而是让每个变化都有明确的**输入、状态、参照、反例与边界**。

同权重才谈缓存等价；改架构就做受控比较；相同形状不等于相同语义；负例必须真的算错而被抓住；性能数字必须连同测量条件；最后把所有尚未证明的东西写进模型卡。做到这些，才有资格把“能跑”推进为“知道为什么这次结果可信”。
